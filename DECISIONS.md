# DECISIONS — Журнал архитектурных решений

Формат: контекст · решение · обоснование · обратимость.

---

## DEC-001. Стек интеграционного сервиса: .NET 8 / ASP.NET Core / Windows Service / SQLite(WAL)
- **Контекст:** нужен надёжный серверный сервис рядом с 1С (Windows).
- **Решение:** зафиксировано ТЗ п.4.2 — принимаем как базовый стек.
- **Обоснование:** нативно для Windows Server рядом с 1С; Windows Service для
  автозапуска; SQLite(WAL) — лёгкое встраиваемое хранилище очередей/mapping/логов
  без отдельной СУБД; структурированные логи.
- **Обратимость:** средняя (замена хранилища возможна за абстракцией репозиториев).

## DEC-002. Никакого прямого доступа к БД 1С — только HTTP-контракт
- **Контекст:** соблазн читать таблицы SQL 1С напрямую.
- **Решение:** обмен исключительно через HTTP-методы расширения 1С (JSON), запрет
  прямого доступа к БД (ТЗ п.4, п.21.4).
- **Обоснование:** сохранность учёта, поддержка обновлений 1С, безопасность,
  корректное проведение документов средствами платформы.
- **Обратимость:** низкая (осознанно, это архитектурный инвариант).

## DEC-003. Сторона 1С — расширение `.cfe`, минимально инвазивно
- **Контекст:** нужны HTTP-методы и реквизит внешнего ID в 1С.
- **Решение:** реализовать через расширение конфигурации, по возможности **не меняя**
  основную конфигурацию; внешние ID — в `РС.ВнешниеИдентификаторыKeyCRM`.
- **Обоснование:** ТЗ п.4.1, п.21.3; изоляция доработок, простота отката.
- **Обратимость:** зависит от R-01 — при несовместимости платформы применяется
  обходной путь (см. `01_SYSTEM_AUDIT.md` B.1). **Финализируется после BLK-002.**
- **Статус:** предварительное, ожидает подтверждения версии платформы.

## DEC-004. Единый истинный остаток — 1С
- **Решение:** 1С — единственный источник фактического остатка; KeyCRM хранит
  оперативную копию + оперативный резерв; после каждого значимого события —
  обновление KeyCRM из 1С.
- **Обоснование:** ТЗ п.5.3; исключение двух независимых истин.
- **Обратимость:** низкая (бизнес-инвариант).

## DEC-005. Идемпотентность и связка по стабильным ID
- **Решение:** товар — `sku`/`offer_id`; заказ — `order.id`; покупатель — `id`+
  телефон/email; документ 1С — GUID; оплата — `payment.id`; событие — ключ
  идемпотентности. Повторная операция не создаёт дубль.
- **Обоснование:** ТЗ п.6.3, п.15; защита от повторных вебхуков и двойного списания.
- **Обратимость:** низкая.

## DEC-006. Пер-складские остатки — через `GET /offers/stocks`, не через вебхук
- **Решение:** см. `KEYCRM_LIMITATIONS.md` LIM-01.
- **Обоснование:** вебхук агрегирует склады.
- **Обратимость:** высокая (пересмотр при изменении API KeyCRM).

## DEC-011. Ключ сопоставления товаров: штрихкод → артикул-код+характеристика (fallback)
- **Контекст (docs/06):** SKU KeyCRM (`2000000…`) в выгрузках 1С не найдены;
  совпадает артикул-код в названии (AM52231.003 и т.п.) — 929 кодов в обеих системах.
- **Решение:** трёхуровневое сопоставление в обработке 1С:
  1) по штрихкоду (регистр Штрихкодов) — если 1С хранит `2000000…`;
  2) fallback — по артикул-коду, извлечённому из названия, + характеристика (цвет),
     с нормализацией (Шанталье/Шантилье, суффикс `_(1)`, регистр);
  3) не сопоставлено → `SKU_NOT_FOUND` (заказ не проводится, отчёт расхождений).
- **Проверка до реализации fallback:** подтвердить наличие/отсутствие `2000000…`
  в регистре Штрихкодов 1С (блокер — экспорт штрихкодов или тест `.epf`).
- **Опция:** backfill штрихкодов KeyCRM в 1С, чтобы дальше работать по штрихкоду.
- **Статус:** штрихкод-путь реализован в `.epf`; fallback добавляется после проверки.
- **Обратимость:** высокая.

## DEC-010. Остатки в KeyCRM — один склад с суммарным остатком (подтверждено владельцем)
- **Контекст (факт 2026-07-16):** в KeyCRM настроен ОДИН склад «Основной»;
  в 1С — 6 мест хранения. Владелец выбрал показывать в KeyCRM суммарный остаток.
- **Решение:** KeyCRM хранит один склад; middleware пишет туда **сумму доступных
  остатков** по всем 6 местам из 1С (`available` = Σ по местам) через
  `PUT /offers/stocks` на «Основной». Пер-складская детализация остаётся только в 1С.
- **Следствия (упрощения):**
  * LIM-01 (вебхук агрегирует склады) и LIM-03 (нет пер-складского чтения) —
    **больше не проблемы**: нам и нужен агрегат.
  * Сверка тривиальна: Σ(1С по 6 местам) ↔ `GET /offers/stocks` (агрегат KeyCRM).
- **Открытый под-вопрос (склад отгрузки для документов 1С):** заказу в 1С всё равно
  нужен конкретный склад для резерва/реализации. Менеджер в KeyCRM его не выбирает.
  **Решение по умолчанию:** склад отгрузки = настраиваемый «склад по умолчанию»
  (предлагается **Магазин №4** — основная сборка); при необходимости позже добавим
  необязательное поле заказа «склад отгрузки» (select → 1С). Меняется в конфиге.
- **Обратимость:** высокая — если позже понадобится детализация, переходим на 6
  складов KeyCRM без переписывания ядра (остатки уже идут по-складски из 1С).

## DEC-009. Транспорт middleware↔1С: абстракция коннектора; кандидат — COM (вариант B)
- **Контекст (факты 2026-07-16):** платформа 8.3.18.1334, но конфигурация УТП УА
  ред. 1.2.35.1 — эпохи 8.2 (обычное приложение), база **файловая**. С высокой
  вероятностью режим совместимости 8.2.x → расширения `.cfe` и HTTP-сервисы
  недоступны независимо от версии платформы.
- **Решение:** middleware проектируется с интерфейсом `I1CConnector` (логические
  операции контракта `05_API_CONTRACT.md`); первый драйвер — **COM**
  (`V83.COMConnector` + внешняя обработка `.epf` с экспортными функциями),
  без изменения конфигурации и без веб-публикации. Драйвер HTTP добавляется,
  если/когда доступен вариант A или C.
- **Обоснование:** работает на файловой базе сегодня; нулевое вторжение в
  конфигурацию; синхронные вызовы (резерв — секунды, не поллинг); лицензий
  достаточно (HASP 100+50). Матрица вариантов — `handover-1c/02_1C_ENVIRONMENT.md`.
- **Следствие для контракта:** `05_API_CONTRACT.md` остаётся логическим контрактом
  (операции/поля/ошибки/идемпотентность те же); физический транспорт — экспортные
  функции обработки вместо HTTP-эндпоинтов; OpenAPI сохраняется как спецификация
  на случай будущего HTTP-драйвера.
- **Статус:** предварительное до проверки режима совместимости в Конфигураторе.
- **Обратимость:** высокая (архитектура с абстракцией именно для этого).

## DEC-008. Единая валюта обмена — USD, без автоконвертации
- **Контекст:** источник Prom работает в UAH; остальные источники и учёт — USD.
- **Решение (подтверждено владельцем 2026-07-16):** вся валюта в 1С и KeyCRM — USD.
  Заказы с Prom сотрудники пересчитывают в гривню **вручную**; интеграция
  **не выполняет** автоматическую конвертацию валют и передаёт суммы как есть (USD).
- **Обоснование:** прямое указание заказчика; исключает риски курсовых расхождений
  внутри обмена.
- **Контроль:** если в заказе `currency_code ≠ USD` на момент синхронизации в 1С —
  заказ не проводится автоматически: запись в журнал конфликтов + статус
  «Ошибка синхронизации» с причиной «валюта не USD, требуется ручной пересчёт».
- **Обратимость:** высокая (мультивалютность можно добавить отдельным этапом).

## DEC-007. Сборка — на стандартном интерфейсе KeyCRM (без отдельного приложения)
- **Решение:** Этап 1 сборки — роли + статусы + печатный лист KeyCRM; отдельное
  приложение сборщика не разрабатывать до доказанной недостаточности.
- **Обоснование:** ТЗ п.9, правило Claude №14 (не плодить интерфейсы).
- **Обратимость:** высокая (Этап 2 сборки предусмотрен).
