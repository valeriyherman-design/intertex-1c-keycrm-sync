# 03. Целевой рабочий процесс (Target Workflow)

**Проект:** KeyCRM ↔ 1С:УТП · **Дата:** 2026-07-16 · **Этап:** 1

Главный принцип: **менеджер/сборщик работают только в KeyCRM**; каждое значимое
изменение статуса — это команда интеграционному сервису, который выполняет операцию
в 1С и возвращает факт (остатки, номер документа) обратно в KeyCRM.

Формат: статус → кто переводит → действие KeyCRM → действие Integration Service (IS)
→ действие 1С → резерв? → списание? → откат? → статус при ошибке.

**Ключевые инварианты:**
- Списание (реализация в 1С) происходит **только** на переходе 12→13 после явной
  проверки, а не при случайной смене статуса (ТЗ п.10).
- Статусы 5, 13, 19 переводит **сам сервис** (авто) — менеджер не может вручную
  объявить «зарезервировано»/«списано» без подтверждения 1С.
- Любой сбой IS/1С → статус 19 с человекочитаемой причиной и задачей ответственному.

> Точный маппинг этих 19 бизнес-статусов на реальные статусы/воронки KeyCRM
> (`GET /order/status`, Pipelines) — после BLK-001. Право перевода по статусам —
> через роли KeyCRM (см. Раздел 6).

## Раздел 2. Сценарий резервирования (ТЗ п.8)

Триггер: менеджер → статус **«Проверка резерва»** (4).

```
Webhook (order status = Проверка резерва)
  └─> IS: сохранить событие в очередь, вернуть HTTP 200 немедленно
  └─> IS: GET /order/{id}?include=... — полный состав заказа
  └─> IS: валидация
        • обязательные поля заполнены?
        • все SKU сопоставлены с 1С?
        • склад отгрузки определён и сопоставлен?
        • дробные количества корректны (ткань в метрах)?
  └─> 1С (HTTP-сервис расширения): создать/обновить ЗаказПокупателя (идемпотентно по order.id)
  └─> 1С: выполнить резерв
  └─> 1С: вернуть подтверждение (успех | нехватка по позиции X кол-во Y)
  ├─ успех:
  │     └─> KeyCRM: обновить остатки (/offers/stocks)
  │     └─> KeyCRM: статус → «Зарезервирован» (5)
  └─ неуспех (нехватка/ошибка):
        └─> НЕ создавать фиктивный резерв
        └─> KeyCRM: статус → «Ошибка синхронизации» (19)
        └─> KeyCRM: причина в кастомное поле (позиция + дефицит)
        └─> KeyCRM: задача ответственному менеджеру
```

Идемпотентность: повторный вебхук того же перехода не создаёт второй ЗаказПокупателя
(ключ = order.id + тип операции).

## Раздел 3. Сценарий сборки (ТЗ п.9)

Триггер: оплата/разрешение руководителя → статус **«На сборку»** (9).

**Сборщик видит (роль «Сборщик» в KeyCRM):** № заказа, склад, место хранения
(если есть в 1С), **штрихкод (базовый EAN-13)**, **внутренний оригинальный код/
название товара** (складовщику он нужен для поиска на складе — DEC-012), фото,
название, цвет/характеристики, требуемое кол-во, ед. изм., комментарий менеджера,
способ упаковки, способ доставки.

**Сборщик НЕ видит:** закупочную цену, маржу, финансы, лишнюю переписку,
данные других клиентов, заказы не в сборке.

> **Видимость внутреннего кода (DEC-012):** «оригинальное название»/артикул —
> вторичная внутренняя информация, только для складовщика и сотрудника размещения
> заказа. **Менеджеры и клиенты его видеть не должны.** В KeyCRM данные при этом не
> меняем (правило владельца) — вопрос решается ролями и составом листа сборки.

**Этап 1 (сейчас):** стандартный интерфейс KeyCRM — роли, статусы, печатный лист
сборки. Отдельное приложение сборщика **не разрабатывается**, пока не доказана
недостаточность стандартных средств (ТЗ п.9, правило Claude №14).

**Этап 2 (потенциально):** скан штрихкода камерой, поштучное подтверждение,
фиксация фактически собранного, запрет завершения при расхождении, фото заказа.

## Раздел 4. Списание и реализация (ТЗ п.10)

Триггер: статус **«Проверка перед списанием»** (12) → авто-переход в 13.

```
IS: проверить наличие резерва по заказу
IS: проверить собранное количество == состав заказа
IS: проверить отсутствие изменений заказа с момента резерва (контрольная сумма)
  ├─ всё сходится:
  │   └─> 1С: создать/обновить Реализацию (идемпотентно) и ПРОВЕСТИ
  │   └─> 1С: вернуть подтверждение проведения + № документа + GUID
  │   └─> KeyCRM: обновить остатки; № документа/дата/GUID → кастомные поля
  │   └─> KeyCRM: статус → «Готов к отправке» (13)  [здесь фиксируется списание]
  └─ ошибка проведения (закрытый период / отрицательный остаток / др.):
      └─> НЕ переводить в финальный статус, НЕ повторять списание
      └─> KeyCRM: статус → «Ошибка синхронизации» (19)
      └─> KeyCRM: текст ошибки 1С в кастомное поле + задача ответственному
```

## Раздел 5. Отмена и возврат (ТЗ п.13)

| Стадия отмены | Действие 1С | Действие KeyCRM |
|---|---|---|
| До резервирования | ничего (документа нет) | закрыть заказ (Отмена) |
| После резервирования, до реализации | снять резерв в ЗаказеПокупателя | вернуть остаток, статус Отмена |
| После реализации | **не удалять реализацию**; создать и провести Возврат | после подтверждения обновить остатки, статус Возврат |
| Частичный возврат | Возврат на точный состав/кол-во | хранить состав возврата отдельно |
| Брак/обмен | отдельный документ (по правилам 1С) | пометка причины |

Принцип: удаление данных исходного заказа **не** используется как способ учёта возврата.

## Раздел 6. Роли и права (KeyCRM)

| Роль | Может переводить в статусы | Видит финансы | Видит переписку | Видит внутр. код (DEC-012) |
|---|---|---|---|---|
| Менеджер | 1–9, 17, 18 | да (своё) | да (свои клиенты) | **нет** |
| Удалённый менеджер | 1–8 (ограниченный доступ) | ограниченно | свои клиенты | **нет** |
| Сборщик / складовщик | 10, 11 | **нет** | **нет** | **да** |
| Сотрудник размещения заказа | — (размещение) | по потребности | — | **да** |
| Руководитель | все, включая 12, разбор 19 | да | да | да |
| Integration Service | 5, 13, 19 (авто) | — | — | — |

> Точные роли и права — по факту (`GET` пользователей/ролей, BLK-001). Настройка
> ролей и печатных шаблонов — стандартными средствами KeyCRM (без доп. интерфейса).

## Раздел 7. Периодические фоновые процессы

- **Сверка изменённых заказов:** polling `GET /order?filter[updated_at]>...` —
  страховка на случай пропуска вебхука.
- **Сверка остатков:** периодический `GET /offers/stocks` из 1С → KeyCRM
  (единый истинный остаток — 1С; ТЗ п.5.3).
- **Полная сверка по требованию:** кнопка в админ-панели.
- **Health-check и алерт** при длительном отсутствии обмена.

Все фоновые процессы, повторы и backoff проектируются на Этапе 2 (каркас middleware)
после снятия блокеров.
