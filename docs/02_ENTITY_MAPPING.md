# 02. Матрица соответствий сущностей (Entity Mapping)

**Проект:** KeyCRM ↔ 1С:УТП для Украины · **Дата:** 2026-07-16 · **Этап:** 1

Обозначения направления:
- `1С → KeyCRM` — 1С владелец, данные текут в KeyCRM;
- `KeyCRM → 1С` — KeyCRM владелец, данные текут в 1С;
- `↔` — двунаправленно с правилом разрешения конфликтов.

Обозначения достоверности: ✅ факт · 🟡 типовое (подтвердить) · ❓ уточнить.

## Таблица 2. Ключи идентификации (анти-дубли, анти-циклы)

| Сущность | Первичный ключ связи | Резервный поиск | Где хранится обратная ссылка |
|---|---|---|---|
| Товар/вариант | **штрихкод** (`offer.sku`=EAN-13) ↔ регистр Штрихкодов 1С (DEC-011) | артикул из названия + характеристика (fallback) | `РС.ВнешниеИдентификаторыKeyCRM` (в расширении 1С) |
| Склад | mapping-таблица (в middleware) | — | БД middleware `warehouse_map` |
| Заказ | KeyCRM `order.id` | — | кастомное поле заказа `1c_order_guid` + БД middleware |
| Покупатель | KeyCRM `buyer.id` | телефон + email | `РС.ВнешниеИдентификаторыKeyCRM` |
| Документ 1С | GUID ссылки 1С | — | кастомное поле заказа `1c_doc_number`/`1c_doc_guid` |
| Оплата | KeyCRM `payment.id` | — | БД middleware `payment_map` |
| Событие/вебхук | ключ идемпотентности (хэш) | — | БД middleware `idempotency_keys` |

**Правило анти-цикла:** запись, инициированная синхронизацией, помечается флагом
источника; входящее изменение с тем же флагом и неизменным содержимым **не порождает**
обратную синхронизацию (сравнение по контрольной сумме значимых полей).

## Таблица 3. Правила по каждой сущности

Для каждой строки Таблицы 1 фиксируются (заполняется по мере снятия блокеров):

- **Создание:** условие и обязательные поля (напр. Контрагент в 1С требует
  Договор+Организацию 🟡 — подтвердить).
- **Обновление:** какие поля обновляемы, какие «только чтение».
- **Удаление:** запрещено как способ учёта — вместо удаления архивация/сторно
  (ТЗ п.13, п.6 правил Claude).
- **Разрешение конфликтов:** по колонке «Конфликты» Таблицы 1; молчаливая
  перезапись запрещена (ТЗ п.12 оплаты) — при расхождении запись в журнал конфликтов.
- **Частота синхронизации:** товары/цены — по вебхуку + периодическая полная сверка;
  остатки — по вебхуку + периодическая сверка; заказы — по вебхуку статусов
  (near-real-time); полная сверка — по расписанию и по требованию из админ-панели.

> Детализация правил создания/проведения зависит от учётной логики УТП (B.5 в
> `01_SYSTEM_AUDIT.md`) и **заблокирована** до получения данных `04_DATA_REQUEST.md`.
