# Журнал ограничений KeyCRM

Ведётся по требованию устава: для каждого случая, где стандартных средств KeyCRM
недостаточно или поведение накладывает ограничение на интеграцию.

Формат: требуемая функция · что умеет KeyCRM · чего не умеет · как проверено ·
обходной вариант · почему выбран.

---

## LIM-01. Остатки по каждому складу через вебхук

- **Требуемая функция:** видеть в KeyCRM остаток по каждому из 6 мест хранения.
- **Что умеет KeyCRM:** хранит остатки по складам; отдаёт/принимает их через
  `GET /offers/stocks` и `PUT /offers/stocks` (есть привязка к складу).
- **Чего не умеет:** вебхук изменения остатков отдаёт `offer_id`, `sku`,
  `in_stock`, `in_reserve` и **агрегирует** выбранные склады — payload вебхука
  **не содержит разбивки по складам**.
- **Как проверено:** официальная справка KeyCRM «Transferring Balance Changes via
  Webhook» (help.keycrm.app) — подтверждено 2026-07-16.
- **Обходной вариант:** пер-складскую картину синхронизировать через
  `GET /offers/stocks` (по расписанию + при событии), вебхук использовать как
  триггер «что-то изменилось», а точные значения по складам брать из API.
- **Почему выбран:** не требует доп. интерфейса, использует штатный API,
  сохраняет 1С единственным истинным источником остатка.

## LIM-02. Лимит частоты API — 60 запросов/мин на ключ

- **Требуемая функция:** массовая выгрузка каталога/остатков (>10 000 товаров) и
  оперативная обработка заказов.
- **Что умеет KeyCRM:** REST API с пагинацией, массовый импорт (`/products/import`
  до 100, `/order/import` до 50).
- **Чего не умеет:** обрабатывать более **60 запросов/мин на один ключ**.
- **Как проверено:** официальная документация KeyCRM (help/docs) — 2026-07-16;
  фактический лимит тарифа подтвердить в кабинете (BLK-001).
- **Обходной вариант:** очередь запросов с ограничителем частоты и экспоненциальным
  backoff; массовые операции — батчами через `*/import`; полная сверка — по расписанию.
- **Почему выбран:** прямое требование ТЗ п.15 (ограничение частоты, backoff).

## LIM-03. Чтение остатков по складам через API невозможно

- **Требуемая функция:** читать из KeyCRM остаток по каждому из 6 мест хранения
  (для сверки).
- **Что умеет KeyCRM:** `PUT /offers/stocks` **записывает** остатки по-складски
  (`warehouse_id` обязателен); `GET /offers/stocks` возвращает только агрегат
  (`quantity`, `reserve` итого по всем складам).
- **Чего не умеет:** отдавать разбивку по складам; `filter[warehouse_id]`
  игнорируется.
- **Как проверено:** живые запросы к аккаунту InterTex-Fabric 2026-07-16
  (ответы идентичны с фильтром и без) + модель `OffersStocksUpdateRequest` SDK.
- **Обходной вариант:** middleware хранит «что записано в KeyCRM по каждому складу»
  в своей БД (last-pushed snapshot); сверка: сумма по складам 1С ↔ агрегат
  `GET /offers/stocks`. Расхождение → полная перезапись `PUT` по каждому складу.
- **Почему выбран:** 1С — единственный истинный остаток (DEC-004), поэтому
  обратное чтение из KeyCRM нужно только для контроля, и контроль по агрегату
  достаточен для обнаружения расхождений.

## LIM-04. Нет API-эндпоинта списка складов

- **Требуемая функция:** автоматически получить список складов KeyCRM и их ID
  для таблицы соответствий.
- **Что умеет KeyCRM:** склады ведутся в кабинете; `warehouse_id` фигурирует в
  `PUT /offers/stocks` и в данных заказа (`products.warehouse`).
- **Чего не умеет:** `GET /warehouse|warehouses|storages` → 404 (проверено 2026-07-16).
- **Обходной вариант:** ID складов вводятся в mapping-таблицу вручную из кабинета
  KeyCRM (Настройки → Склады) при первичной настройке; валидация — пробной записью
  остатка одного тестового SKU на тестовом складе.
- **Почему выбран:** склады — статичный справочник (6 мест, меняется редко),
  ручной ввод при установке дешевле и надёжнее скрейпинга кабинета.

## Раздел «на проверку» (после получения ключа BLK-001)

Ниже — пункты, которые нужно проверить живыми запросами, чтобы подтвердить/опровергнуть
как ограничение (пока НЕ считаются ограничениями, требуют проверки):

- Точный перечень **событий вебхуков** и имена action — снять из кабинета
  (Настройки → Вебхуки); Open API их не отдаёт.
- Возможность через API проставлять **произвольный статус** заказа
  (`PUT /order/{id}` со `status_id`) — проверить на тестовом заказе (Этап 2).
- Поддержка **дробных количеств** в позициях заказа (ткань 12.5 м) — поле
  `quantity` в живом заказе видели как целое; тип (float?) проверить тестовым
  заказом. ⚠️ Связано: `unit_type` товаров в аккаунте сейчас пуст (см. снапшот §5).
- Наличие способа привязать **PDF документа 1С** к заказу
  (`POST /order/{id}/attachment/{fileId}` + Storage API) — проверить на тесте.
- Ограничения **фильтра `filter[updated_at]`** и набора значений `include` — при
  разработке клиента API (Этап 2).
