## 3. Сопоставление товаров 1С ↔ KeyCRM (уточнено владельцем 2026-07-16)

> ✅ **Уточнение владельца:** базовый идентификатор — **EAN-13 штрихкод `2000000…`**
> (он же SKU в KeyCRM), по нему ориентируется бизнес → сопоставление **по штрихкоду —
> основной путь** (DEC-011); артикул — вторичный. «Оригинальное название»/артикул —
> вторичная внутренняя информация (DEC-012), видят только складовщик и сотрудник
> размещения заказа.
> ⚠️ **Но:** «0 совпадений» ниже опровергает лишь тезис «штрихкодов нет» (в выгрузке
> просто не было колонки штрихкодов), но **не доказывает**, что они есть в регистре
> Штрихкодов 1С. Учитывая последовательность SKU (+7) в «магазинном» EAN-диапазоне,
> они могли быть сгенерированы в KeyCRM. Состояние — **гипотеза, требующая проверки**
> (R-12 открыт, гейт в DEC-011).

**Три разных идентификатора:**

| Система | Идентификатор | Пример |
|---|---|---|
| 1С Код | внутренний | `3869` |
| 1С Артикул | 6-значный (94% заполнен) | `388168`, `375665` |
| KeyCRM SKU | **сгенерированный штрихкод EAN**, последовательный (+7) | `2000000310039`, `…046`, `…053` |

**Проверка (факт):** штрихкодов `2000000…` в **выгрузках** 1С — **0**
(но в выгрузке не было колонки штрихкодов — только Код и Артикул). → это **не значит**
их отсутствия в 1С; вопрос открыт до проверки регистра Штрихкодов (R-12). Возможны оба
исхода: 1С тоже автогенерирует «магазинные» штрихкоды `20xxxxx` (тогда совпадут), либо
SKU сгенерированы только в KeyCRM (тогда сопоставление по штрихкоду не сработает).

**Что реально совпадает:** **артикул-код в названии** формата
`[A-Z]{2}\d{4,6}(\.\d{2,3})+` (AM52231.003, RJ11235.002.05, AB13316.102) —
найдено **929** таких кодов в 1С и они же зашиты в названия товаров KeyCRM
(«Шантилье **AM52231.003**_(1)»). Плюс характеристика/цвет (Молочный/Белый).

**Следствие для стратегии (DEC-011):**
1. Приоритет 1 — по **штрихкоду** (базовый ключ владельца). ⚠️ Работает, только
   если регистр Штрихкодов 1С содержит `2000000…` — **проверить (ГЕЙТ R-12)**.
2. Приоритет 2 (fallback) — по **артикул-коду из названия + характеристика**.
   Требует нормализации («Шанталье»/«Шантилье», суффикс `_(1)`, регистр) и
   разового отчёта расхождений. Покрытие ~929/3777 (~25%) — при провале штрихкода
   остаток каталога без ключа → массовый `SKU_NOT_FOUND`.
3. Что не сопоставилось — в отчёт, товар в заказе с таким SKU → `SKU_NOT_FOUND`
   (заказ не проводится молча).

> Обработка `.epf` уже ищет по регистру Штрихкодов, затем по коду 1С. ⚠️ Заказ KeyCRM
> несёт SKU=штрихкод (не внутренний Код 1С), поэтому текущая ветка «по Коду» им не
> кормится — **артикул-fallback ещё нужно реализовать** (TODO Этапа 3), иначе при
> промахе по штрихкоду сопоставление полностью падает.

## 4. Качество каталога (влияет на Этап 3)

> ✅ **Уточнение владельца (2026-07-16):** расхождение каталогов 1С↔KeyCRM —
> **нормально**: часть товаров неактуальна (не возят), часть — новые, добавленные в
> KeyCRM ПОСЛЕ ручной выгрузки базы. → правило синхронизации: интеграция **не удаляет
> и не помечает ошибкой** товары KeyCRM, которых нет в текущей выгрузке 1С.
> **Аудит каталога KeyCRM (3074 товара, 2026-07-16, read-only):** дублей названий 0,
> товаров без цены и без вариантов 0. Каталог чистый. ~6 «заглушечных» кодов
> (`00000`, `7777`, `8888`, `Noiiiii`, `Y0001AL`, `RJ11110..002.11`) **проверены по
> 1С: все РЕАЛЬНЫЕ товары** с кодами/артикулами; названия идентичны 1С↔KeyCRM (двойная
> точка `..` — тоже из 1С, не опечатка KeyCRM). Остатки: Гіпюр 00000 ≈21.2 м, Y0001AL
> ≈37.25 м, Noiiiii 7 пар — есть текущий остаток; 7777/A, 8888, RJ11110..002.11 —
> распроданы (0), но с историей движения. → **исправлять нечего.** Артикул в названии
> совпадает 1С↔KeyCRM → вторичный ключ (по артикулу) рабочий. `unit_type` пуст у 100%
> — заполнить из 1С.

- Явный мусор/тест в **номенклатуре 1С**: `__фііфвфів`, `-вапифвпфа`, `========`,
  `------------`, `0.9`, `1`, `_вільно`, `_Інші тканини_ (*)` — ~11 очевидных,
  плюс группы-заглушки. При выгрузке 1С→KeyCRM — **фильтровать** (не переносить
  помеченные на удаление / служебные группы).
- ~3777 позиций номенклатуры 1С; в KeyCRM ~5399 вариантов (offers) — разница за счёт
  характеристик (цветов) и, возможно, ранее импортированных/дублей.

## 5. Подтверждение сопоставления (не блокер — владелец подтвердил ключ)

Владелец подтвердил, что EAN-13 штрихкод — базовый идентификатор, поэтому это уже
не риск-блокер, а быстрая проверка. Нужно лишь убедиться, что регистр Штрихкодов 1С
содержит `2000000…`:
- **Экспорт штрихкодов из 1С:** Номенклатура + Характеристика + **Штрихкод**;
- либо один запрос обработки `.epf` к регистру Штрихкодов на тестовой базе.

Ожидаемо **да** → сопоставление по штрихкоду (основной путь уже в `.epf`).
Если у части товаров штрихкода нет — для них вторичный fallback по артикул-коду
из названия + характеристика (929 кодов совпадают в обеих системах).
